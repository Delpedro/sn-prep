8
Upgrades
+
💡 Why it's safe by prod: same upgrade done twice already. Decisions and fixes travel in update sets. Prod isn't the first attempt.
Before
→Review release + upgrade notes against our instance
→Check for bottlenecks, then schedule via Now Support
→Comms to dev users — export or promote your update sets
Dev
→Clone → upgrade
→Spin up an update set, capture the skipped-record decisions in it
→Functional testing (not UAT) — incident, problem, change + CAB, service requests, portal
→Anything off → log a bug in production, reviewed by architect / platform owner / process owner
→Fixes in a correctly named update set → promote
Test
→Sign-off first
→Schedule clone + upgrade, comms again
→UAT testers — test scripts, plus how people actually use it
→Defects → logged in prod → update set → fixed and functionally tested in dev → promoted to test → retested
Prod
→CAB approval — business, CAB, product owner
→Comms out, go-live announced
→Hypercare at least a week
💡 What actually made it work: put a PM on the upgrade. Before, a team member ran it alongside P1s — bogged down, rushing, chasing UAT consultants across every area of the business. PM chases, tech person does the tech.

Terminology

CI classthe table it lives in. Wrong class = duplicates.
Relationshipsruns on / depends on / used by — what breaks when one thing falls over
Dependency mapvisual of those relationships
Business servicewhat the business cares about, sitting on top of CIs
Discovery sourcewhere the record came from
MID Serveroutbound only, sits in the estate, does the scanning
ECC queuethe in/out tray between instance and MID Server
Probes / sensorsprobe goes out, sensor makes sense of what came back
Patternsnewer replacement for probes/sensors

Identification rulesis this the same box we already have?

Authoritative sourcethe source allowed to win for that field
